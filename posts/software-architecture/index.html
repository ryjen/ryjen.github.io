Software Architecture for Independence

By Robert Ryan Jennings Published Apr 17, 2025 12:25PM 18 min read Updated Oct 23, 2026 12:00AM

software engineering
software architecture clean architecture solid ai security mobile redux

Originally published on Medium on April 17, 2025. Edited October 23, 2026 for clarity, technical accuracy, and lessons from production systems and independent engineering projects. The original article includes illustrations not yet reproduced locally.

The value of software architecture is not measured by the number of layers, interfaces, or design patterns in a system. It is measured by how much change the system can absorb without disturbing unrelated behavior.

A user interface will change. A database or external API may be replaced. A third-party library will be upgraded. Requirements, security assumptions, teams, and delivery constraints also change. Architecture cannot eliminate that uncertainty, but it can determine how far each change propagates.

Independence is the goal. Layers, use cases, SOLID principles, and design patterns are techniques for achieving it—not goals in themselves.

This article looks at those techniques and where I have found them useful in mobile applications, legacy modernization, security-sensitive systems, and more recently AI-assisted development. It also covers where abstraction becomes an expense rather than a benefit.

1. The Cost of Change

The familiar project management triangle describes tensions among scope, time, and cost, with quality affected by how the work is managed. It is a planning model, not a law that precisely limits teams to optimizing two variables.

Architecture influences these trade-offs by changing the cost of a change. A feature that can be implemented and tested in one bounded component is usually easier to estimate than one that touches navigation, business rules, persistence, and several remote services at once.

Good boundaries can make it easier to:

  • Change an external implementation without rewriting business policy.
  • Develop independent features without coordinating every modification.
  • Test important behavior without bringing up the entire application.
  • Diagnose regressions at a known contract or ownership boundary.
  • Transfer knowledge through consistent interfaces and conventions.

There is a cost on the other side of the ledger. Each abstraction introduces another concept, contract, and potential source of indirection. Splitting a small feature into six packages will not necessarily make it more maintainable. The relevant question is whether the boundary isolates a meaningful source of change, complexity, or risk.

I saw the leverage of reuse in product work at QuickMobile/Cvent, where a configurable conference framework supported many event-specific experiences. A change to shared platform behavior could benefit more than one event, rather than becoming another client-specific fix. That leverage depended on keeping the common framework distinct from event configuration.

2. Clean Architecture Fundamentals

Clean Architecture offers a way to organize software around policies that are important to the application rather than the tools used to implement them.

It is useful to think of two different ways to divide a system:

  • Horizontally: responsibilities such as presentation, application coordination, domain policy, and infrastructure.
  • Vertically: features or use cases such as authentication, retrieving a document, synchronizing a change, or generating a report.

A layer is a logical boundary. It may correspond to a package or module, but folders alone do not enforce it. A use case is a bounded operation that coordinates the responsibilities necessary to achieve an outcome.

The central rule concerns source-code dependencies: policy should not need to import a specific database driver, UI framework, or remote service SDK to express itself.

For example, a domain-facing use case can require a session store contract. An infrastructure adapter implements that contract using a particular storage mechanism. At runtime, the use case calls outward through the interface; at source level, the infrastructure implementation depends inward on the contract.

That distinction matters. Runtime data flow and source dependency direction are not the same thing.

2.1 SOLID Principles

SOLID provides useful review questions for individual units of code and their relationships. It does not prescribe a package layout or require every class to have an interface.

Consider an authentication feature whose policy must work with different identity providers, session stores, and user interfaces.

Single Responsibility Principle (SRP)

A module should have one principal reason to change, understood in terms of the people or concerns that own its requirements. Credential verification, presentation rendering, and analytics reporting need not be maintained as one unit simply because they all happen during login.

Open-Closed Principle (OCP)

A well-chosen extension point can accommodate a new authentication provider without repeatedly changing the core login policy. That does not mean code should never be modified. The goal is to protect stable behavior from the kinds of variation the design genuinely expects.

Liskov Substitution Principle (LSP)

An implementation must preserve the behavioral contract expected by callers. If a token-validation adapter silently treats expired credentials as valid, it is not a safe substitute for another adapter that rejects them—even when both implement the same method signature. Error behavior and invariants are part of substitutability.

Interface Segregation Principle (ISP)

Clients should depend on the capabilities they need, not a large interface containing unrelated operations. A login use case that needs to verify a credential should not have to depend on an identity-provider administration API as well.

Dependency Inversion Principle (DIP)

High-level policy and low-level adapters should depend on appropriate abstractions rather than having high-level policy tied to an SDK or database. Dependency injection can assemble the implementations, but injection is a mechanism—not the principle itself.

Applied together, these ideas make change more local and tests more focused. Applied indiscriminately, they produce layers of interfaces that never isolate anything meaningful.

3. Applying Boundaries

3.1 Packaging by Layer, Feature, or Component

Packaging is a tool for expressing ownership and dependencies.

Package by layer is approachable in a smaller application, but a single feature can require edits across many directories.

Package by feature keeps related presentation, application, and domain behavior closer together. Shared contracts still need deliberate ownership so that features do not become mutually dependent.

Ports and adapters (hexagonal architecture) emphasizes a policy core and interfaces for outside interactions. UI, database, network, and AI provider implementations can be adapters around those ports. Hexagonal architecture is not merely a particular folder layout.

Package by component gives independently usable components explicit public APIs, often with internal layering. It is useful when a component has a clear release or reuse boundary.

These approaches can coexist. A feature-oriented application may use ports and adapters internally and package reusable platform capabilities as components. The structure should reveal how the system changes and who owns those changes.

3.2 Boundaries Need Contracts

An interface is not automatically a boundary. A useful contract specifies more than method names: inputs, outputs, invariants, error semantics, ownership, side effects, and compatibility assumptions.

That is especially important across network and persistence boundaries. At ePACT, mobile/backend work involved relational backend storage, SQLite and JSON-based client models, and change-only synchronization. The important architectural seam was the data contract between heterogeneous stores—not forcing each tier to use the same persistence representation.

A boundary is valuable when it prevents an implementation detail from leaking into a caller’s assumptions. A leaky repository that returns database-specific records throughout a domain does not buy much independence, even if it has an interface.

3.3 Keep Details in Their Place

Some recurring examples:

  • Data is significant; its storage provider is a detail.
  • User experience is significant; its rendering framework is a detail.
  • Business behavior is significant; a particular middleware library is a detail.
  • An AI-assisted capability may be significant; its model vendor is a detail.

This does not mean all details are cheap to replace. A database’s consistency model or a model’s context limitations can shape what the application can guarantee. Independence comes from making such assumptions explicit and confining them—not pretending they do not exist.

3.4 Humble Objects and Testability

The Humble Object pattern separates difficult-to-test integration or presentation mechanics from deterministic behavior that can be tested directly.

A view can be deliberately simple: render state and forward user intent. A presenter or view model prepares that state and makes decisions that can be exercised without a real device or UI framework.

The goal is not to move every line out of the view. It is to keep complex policy and state transformations out of places where testing requires unnecessary framework machinery.

4. Refactoring and Modernization

A clean design on a blank page is easier than improving a system with real users, production dependencies, undocumented behavior, and delivery deadlines. In practice, the second problem matters more.

4.1 The Scout Rule, With a Destination

Leave code better than you found it—but make “better” consistent with the system’s direction. A well-intended cleanup that introduces a new architectural convention for one file can make the codebase less coherent.

A useful incremental sequence is:

  1. Identify a risky or frequently changing behavior.
  2. Record the existing contract and observable outcomes.
  3. Introduce a seam around that behavior.
  4. Change one implementation behind the seam.
  5. Compare results, test the boundary, and observe production behavior.
  6. Remove transitional complexity only when the replacement is proven.

This is compatible with the strangler pattern, partial boundaries, and progressive migration. It avoids needing a complete rewrite before any improvement becomes useful.

4.2 Lessons From Authentication and Asynchronous State

In a retirement-services mobile application at Manulife, the authentication path had accumulated RxJS, Redux thunks, and Promise-based work alongside state-management and view concerns. The biggest issue was not simply the choice of tools. It was determining which operation owned a side effect, when state was read, and what happened when asynchronous work completed out of order.

The practical modernization sequence was to simplify the high-risk login state path, define more consistent state-access and ordering rules, and introduce stronger boundaries incrementally.

This revealed an important distinction: structural separation is not enough if runtime behavior still crosses ownership boundaries unpredictably. An architecture also needs explicit invariants around concurrency, cancellation, state freshness, and side effects.

The work did not replace every asynchronous mechanism with one framework or complete a wholesale Clean Architecture rewrite. The useful outcome was a more disciplined direction for evolving the existing system.

4.3 Prototype, Compare, Then Migrate

A separate analytics modernization effort at Manulife exposed another failure mode. Authentication-derived context, analytics mappings, and asynchronous events were entangled. The risk was not only incorrect metrics: stale authenticated context could also cross a privacy boundary.

I prototyped a replacement using Redux and asynchronous thunks, with tests comparing its generated analytics data against the existing implementation. That was a way to evaluate correctness and reduce migration risk before replacing the live path.

The prototype was not merged into the production application. Some colleagues adapted aspects of the work, but competing delivery priorities prevented the proposed migration from becoming the product’s canonical implementation.

That is part of the architectural lesson: a technically sound migration still needs organizational capacity, a credible rollout plan, and an incentive to adopt it. Tests reduce uncertainty; they do not allocate time or make the business case.

4.4 When a Rewrite Is Appropriate

A rewrite can be justified when the existing structure prevents safe evolution and incremental migration is demonstrably more expensive. But “the architecture would be cleaner from scratch” is not enough.

Before choosing one, assess feature parity, hidden integrations, operational behavior, data migration, security regressions, rollback options, and the cost of maintaining two implementations in parallel.

The preference is not never rewrite. It is preserve verifiable behavior and choose the smallest migration that changes the economics of further work.

5. Design Patterns and Their Limits

Patterns provide vocabulary for recurring structural and behavioral problems. Factory, Adapter, Facade, Strategy, Observer, and Command can all help communicate intent. They are not an architecture by themselves.

A repository is useful when a use case needs domain-oriented data access without depending on the database schema, HTTP client, or persistence lifecycle. Its value comes from the stable contract and mapping—not merely from the class name “Repository.”

A strategy is useful where a policy selects among interchangeable behaviors, such as supported authentication methods. The interface must still define what errors, retries, and security decisions mean across implementations.

A chain of responsibility can compose validation or request-processing steps, but the order, short-circuit behavior, and fail-closed defaults must be explicit. Authorization should not become an accidental consequence of which handler happened to run.

5.1 Singleton Versus Lifetime Management

A global singleton locator can hide dependencies, complicate isolation in tests, and introduce shared mutable-state or concurrency problems. A singleton lifetime managed by dependency injection is different: its dependencies remain visible and the object can still be replaced in tests.

The question is not whether there is exactly one instance. It is whether callers depend on a hidden global implementation and whether shared state has well-defined ownership.

Abstractions and patterns should earn their place. An adapter for one SDK that is unlikely to change may be sufficient; a generalized provider framework with plugin discovery, reflection, and elaborate lifecycle management may be unnecessary.

6. Mobile and Presentation Architectures

Presentation frameworks evolve quickly. The most durable distinction is between application policy and how a platform displays state or invokes that policy.

MVC assigns responsibilities to model, view, and controller, but large controllers can become difficult to maintain when they absorb unrelated application logic. Extracting use cases is one way to avoid that outcome.

MVVM exposes state and actions through a view model. A view model can adapt domain results for display without making presentation state itself the source of business truth.

Redux-style unidirectional data flow can give state transitions a clearer ownership model, with actions, reducers, selectors, and effects. It does not require every application to put state in exactly the same layer, nor does it automatically prevent race conditions. Async work still needs a policy for reading current state and applying results.

On iOS, VIPER and The Composable Architecture offer different decompositions of responsibilities and state flow. On Android, MVI-style designs are common, alongside MVVM and other approaches. None is a universal platform standard that substitutes for the underlying dependency and behavioral contracts.

At OpenArchive, introducing SwiftUI and Jetpack Compose alongside Clean/SOLID design work was an opportunity to separate platform rendering from privacy-oriented application concerns. The useful boundary was not “SwiftUI versus Compose”; it was which behavior could remain testable and consistent despite the platform differences.

Mobile also has unavoidable platform-specific capabilities: biometrics, camera, local storage, notifications, background execution, and network availability. They are important capabilities, but their APIs can be kept behind explicit adapters where doing so protects meaningful application behavior.

6.1 Network Boundaries Are Harder Than Package Boundaries

A mobile application’s trust boundary extends through APIs, authentication state, and remote services. For a legacy application that uses authenticated WebViews, a native UI boundary alone cannot resolve token expiry, data ownership, or injected-JavaScript coupling.

A backend-for-frontend (BFF) can become a practical modernization seam between native clients and older backend services. It can stabilize API contracts while backend internals evolve, although it adds another service to operate and secure.

This was relevant to the Manulife mobile environment, where client-side authentication and backend integration had to coexist with legacy WebView experiences. An API boundary was a more realistic path toward independence than waiting for every legacy dependency to disappear.

7. AI as a Replaceable, Untrusted Component

AI adds a new kind of implementation detail: one that can produce useful output without necessarily being deterministic or trustworthy.

The architectural argument for independent model providers still applies. A use case can request inference through an interface while an adapter handles a hosted or local model, prompt formatting, response parsing, and provider-specific errors.

But model portability is only one concern. A model output should not automatically become an authorization decision, a filesystem mutation, or an instruction to execute code.

7.1 Separate Advice From Authority

In independent projects such as Anthesis, Dubnium, and related engineering tools, I have been exploring and implementing a recurring pattern:

  1. A use case identifies an operation and assembles scoped context.
  2. A model or deterministic rule proposes an action or result.
  3. Deterministic validation checks schema, scope, identity, and invariants.
  4. Policy and explicit approval determine whether execution is permitted.
  5. A constrained executor performs the authorized operation.
  6. Evidence records what was requested, approved, executed, and verified.

These are project-level engineering patterns, not a claim that one unified enterprise platform has been deployed.

The distinction follows Clean Architecture’s original premise: an external intelligence component may influence application behavior without owning the application’s authority.

7.2 Context Is Also a Boundary

Prompts, retrieved documents, model identity, and conversation history all influence an inference result. Treat them as inputs with provenance and scope, not as invisible ambient state.

Retrieval and context assembly can use local files, databases, or vector search, but the originating data still requires access controls, lifetime rules, and validation. A prompt retrieved from a remote source must not silently expand the permissions of the tool that consumes it.

A local model can help with offline availability or data residency. It does not by itself make a workflow secure: tool authority, prompt injection, sensitive-data flow, and model failure remain design problems.

8. Conventions, Reviews, and Testing

Architecture is sustained by conventions that developers can understand and tools can check. It weakens when every feature invents a different way to cross a boundary.

Useful conventions cover dependency direction, interface ownership, error handling, naming, data mapping, state transitions, and where side effects are allowed.

8.1 Example Dependency Rules

A simple set of constraints might be:

  • Domain policy imports neither presentation nor infrastructure code.
  • Application use cases coordinate policy through defined ports.
  • Infrastructure adapters implement ports and can depend on inward contracts.
  • Presentation maps user intent and renders results; business rules do not require a particular view framework.
  • Features expose narrow contracts rather than reaching into one another’s internal state.

These are source dependency rules, not a claim that runtime requests or responses move through the system in only one direction.

Package boundaries and import checks can help enforce the constraints, but engineering judgment is still needed when an abstraction starts leaking implementation details.

8.2 A Practical Test Pyramid

The objective is to detect regressions at the least expensive meaningful boundary, not to maximize mock counts.

  • Unit tests exercise deterministic domain rules and state transitions.
  • Integration tests verify real mappings, persistence adapters, API contracts, and error behavior across subsystems.
  • End-to-end tests cover a smaller number of critical user journeys, especially authentication, synchronization, and recovery.

Dependency injection helps substitute controlled collaborators where appropriate. But an implementation that passes hundreds of mocked unit tests while its real database adapter is broken is not independently verifiable in any useful sense.

At Manulife and OpenArchive, cleaner architectural seams were part of improving unit testability and planning balanced validation across unit, integration, and end-to-end levels. That should not be confused with a claim that every tier of a full automated test pyramid was deployed in CI.

8.3 Reviews Preserve the Architecture

A review should ask more than whether code follows style rules:

  • Does the change respect ownership and dependency direction?
  • Are concurrency and data lifecycle assumptions explicit?
  • Is the new abstraction justified by a real source of variation?
  • Can the behavior be verified at a relevant boundary?
  • Does the change improve the system’s long-term ability to evolve?

In engineering teams I have found code review, focused walkthroughs, and shared design conventions useful for communicating these decisions. A small, reviewable migration with evidence usually travels farther than a large architectural proposal that no one has time to absorb.

9. Security and Data Lifecycles

Clean Architecture can support security by making trust boundaries and control placement visible. It does not automatically provide confidentiality, integrity, availability, least privilege, or non-repudiation.

A dependency boundary is not necessarily a trust boundary. A package interface in one process does not isolate credentials from compromised code executing with the same authority. Controls must exist where data and authority actually cross trust boundaries.

Secure design principles such as least privilege, defense in depth, fail-safe defaults, complete mediation, and economy of mechanism need implementation and verification, not just well-named layers.

9.1 Data in Transit, at Rest, and in Use

Data changes risk as it moves:

  • In transit: authenticate endpoints and protect the communication channel; validate and minimize what crosses the boundary.
  • At rest: manage access, retention, encryption where appropriate, backups, and deletion.
  • In use: treat cached credentials, mutable state, concurrent access, and logs as part of the data’s exposure surface.

Mapping domain data into presentation state is a useful privacy control when it prevents unnecessary fields from reaching a UI or telemetry system. It is not a replacement for backend authorization.

9.2 Authentication State Is Not Just UI State

The Manulife analytics example illustrates why state ownership matters to security. If asynchronous operations carry stale authenticated-user context into a later unauthenticated session, a seemingly ordinary analytics event can become a privacy defect.

More predictable state transitions and explicit mapping boundaries make that risk easier to reason about and test. They do not guarantee that every event is correct; integration tests, security review, and runtime validation still matter.

Likewise, a mobile app that invokes a remote service should not be the final authority over entitlements, token validity, or protected server resources. Client-side checks may improve usability, but security decisions need enforcement at an appropriate trusted boundary.

For more concrete client-side security concerns, see Modern Mobile Hardening.

10. Conclusion

Software architecture is a discipline of choosing what should remain stable when everything around it changes.

Clean Architecture, SOLID, use cases, and design patterns give us useful ways to describe those choices. Their value comes from controlling coupling, localizing change, making behavior testable, and giving teams a shared understanding of ownership.

Experience with long-lived systems adds qualifications that are easy to miss in a diagram: asynchronous state can defeat a tidy package structure; a rewrite can be technically sound and still fail to be adopted; a model abstraction can preserve portability while introducing new execution risks; and a clean interface alone cannot enforce security.

The right design is not the one with the most abstraction. It is the one with boundaries worth maintaining, contracts that can be verified, and a migration path that remains practical under real constraints.
